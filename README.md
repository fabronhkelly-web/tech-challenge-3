# Tech Challenge 3 — Infrastructure as Code with Terraform and Ansible

Provision AWS infrastructure with **Terraform** and configure it with **Ansible**:

- **Terraform** creates an EC2 instance, an S3 bucket, an IAM role (with instance profile and least-privilege policy), a security group and an SSH key pair.
- **Ansible** installs and configures **Nginx** on the instance and deploys a web page that displays **"Hello, World!"**, then proves the IAM role works by uploading that page to the S3 bucket.

```text
┌──────────────── Your computer (VS Code) ────────────────┐
│                                                          │
│  terraform apply ──► AWS resources                       │
│        │                                                 │
│        └─► writes ansible/inventory/hosts.ini            │
│                 (IP, SSH key, bucket name)               │
│                                                          │
│  ansible-playbook site.yml ──SSH──► EC2 instance         │
└──────────────────────────────────────────────────────────┘
```

## Prerequisites

| Requirement | Why |
|---|---|
| An **AWS account** | Where the resources are created |
| An **IAM user access key** with permission to manage EC2, S3 and IAM (e.g. `AdministratorAccess` on a personal/sandbox account) | Terraform authenticates with it |
| **Git** | Clone the repo |
| **Docker Desktop** *(recommended)* — or Terraform ≥ 1.5, Ansible ≥ 2.15 and AWS CLI v2 installed natively | Runs the tools |
| **VS Code** *(optional)* | Editor + integrated terminal |

> **Windows users:** Ansible does not run natively on Windows. Use **Option A (Docker)** below, or run everything inside **WSL** (Option B). No Windows-specific steps are needed beyond that.

## Set up the environment

### 1. Clone the repository

```bash
git clone https://github.com/<your-username>/tech-challenge-3.git
cd tech-challenge-3
code .        # opens the folder in VS Code
```

VS Code will offer to install the recommended extensions (Terraform, Ansible, YAML, WSL) from `.vscode/extensions.json`.

### 2. Create AWS access keys

1. AWS Console → **IAM** → **Users** → your user → **Security credentials** → **Create access key** → *Command Line Interface (CLI)*.
2. Copy the **Access key ID** and **Secret access key** (the secret is shown only once).

> Use an IAM user, not the root account, and never commit keys to Git.

### 3a. Option A — Docker toolbox (recommended, works on Windows/macOS/Linux)

Open a terminal in VS Code (**Terminal → New Terminal**) in the project folder:

```bash
docker compose build                 # one-time: builds the toolbox image (~2 min)
docker compose run --rm toolbox      # opens a shell inside the toolbox
```

Inside the toolbox shell, configure your credentials (saved to your normal `~/.aws` folder, e.g. `C:\Users\<you>\.aws`):

```bash
aws configure
#   AWS Access Key ID:     <paste>
#   AWS Secret Access Key: <paste>
#   Default region name:   us-east-1
#   Default output format: json

aws sts get-caller-identity          # should print your account ID and ARN
```

All commands in the next sections are run **inside this toolbox shell**.

### 3b. Option B — Native tools (Linux, macOS or WSL)

```bash
./scripts/install-tools-wsl.sh       # Ubuntu/WSL; on macOS: brew install terraform ansible awscli
aws configure
aws sts get-caller-identity
```

> **WSL tip:** clone the repo inside your Linux home (`~/tech-challenge-3`), not under `/mnt/c/...`. Windows-mounted folders ignore `chmod`, so SSH would reject the private key and Ansible would ignore `ansible.cfg`.

### 4. (Optional) Customise variables

```bash
cp terraform/terraform.tfvars.example terraform/terraform.tfvars
```

| Variable | Default | Description |
|---|---|---|
| `aws_region` | `us-east-1` | Region to deploy into |
| `project_name` | `tech-challenge-3` | Prefix for every resource name |
| `environment` | `dev` | Environment tag / name suffix |
| `instance_type` | `t3.micro` | Free Tier eligible in most regions |
| `root_volume_size` | `8` | Root disk size in GiB |
| `ssh_allowed_cidr` | `""` | Empty = auto-detect your public IP and allow only that `/32` |
| `ssh_key_dir` | `""` | Where the generated private key is written (Docker sets `/keys`) |
| `s3_force_destroy` | `true` | Let `terraform destroy` delete a non-empty bucket |

## Deploy

### One command

```bash
make deploy          # or: ./scripts/deploy.sh
```

This runs `terraform init` → `terraform apply` → `ansible-playbook site.yml` → an HTTP check from your machine, and finishes with:

```text
SUCCESS: http://<public-ip> is serving 'Hello, World!'
```

### Step by step (to see each stage)

**1 — Provision infrastructure with Terraform**

```bash
cd terraform
terraform init       # downloads the AWS, TLS, local, random and http providers
terraform plan       # preview: 20 resources to add
terraform apply      # type "yes" to confirm
terraform output     # shows the IP, URL, bucket name and SSH command
```

Terraform also writes two files for Ansible:

- `ansible/inventory/hosts.ini` — the instance IP, SSH user/key, bucket name and region
- the SSH private key (`.keys/` natively, or the `/keys` Docker volume)

**2 — Configure the server with Ansible**

```bash
cd ../ansible
ansible-playbook site.yml
```

Expected recap:

```text
PLAY RECAP
tech-challenge-3-dev-web : ok=19  changed=10  unreachable=0  failed=0
```

Running it a second time gives `ok=18 changed=1 failed=0` — the only change is the S3 re-upload, showing the playbook is idempotent.

## How the Terraform code works

| File | What it does |
|---|---|
| `versions.tf` | Requires Terraform ≥ 1.5 and pins providers to compatible major versions (`aws ~> 5.0`, etc.) so builds are reproducible. |
| `providers.tf` | Configures the AWS provider for `var.aws_region` and applies **default tags** (`Project`, `Environment`, `ManagedBy`) to every resource. |
| `variables.tf` | All inputs with types, descriptions, sensible defaults and **validation** (e.g. `ssh_allowed_cidr` must be a valid CIDR, `project_name` must be S3-safe). |
| `data.tf` | Looks up the newest **Ubuntu 24.04 LTS** AMI from Canonical's official account, the account's **default VPC**, and your **public IP** via `checkip.amazonaws.com`. `locals` builds the name prefix (`tech-challenge-3-dev`), the SSH CIDR (your IP `/32` unless overridden) and file paths. |
| `keypair.tf` | `tls_private_key` generates an **ED25519** key; `aws_key_pair` registers the public half with EC2; `local_sensitive_file` saves the private half with `0600` permissions for Ansible. |
| `security_group.tf` | One security group with separate rule resources: **HTTP 80 from anywhere**, **SSH 22 only from your IP**, all outbound allowed (for apt and S3). |
| `s3.tf` | A bucket with a random suffix (names are global), **BucketOwnerEnforced** ownership, **all public access blocked**, **versioning** on and **AES-256 encryption** by default. |
| `iam.tf` | An **IAM role** EC2 can assume; a custom policy granting `ListBucket` on the bucket and `Get/Put/DeleteObject` on its objects **only**; the AWS-managed `AmazonSSMManagedInstanceCore` policy (console shell access via Session Manager); and the **instance profile** that attaches the role to the instance. |
| `ec2.tf` | The **EC2 instance**: Ubuntu AMI, `t3.micro`, the key pair, security group and instance profile, a public IP, **IMDSv2 required**, an **encrypted gp3** root volume. `ignore_changes = [ami]` stops a newer AMI from replacing the server. |
| `ansible_inventory.tf` | Renders `templates/hosts.ini.tftpl` into `ansible/inventory/hosts.ini` — the hand-off from Terraform to Ansible, so no IPs are copied by hand. |
| `outputs.tf` | Instance ID/IP/DNS, website URL, bucket name, role name, security group ID, allowed SSH CIDR and a ready-to-paste SSH command. |

**Resource dependency flow:** key pair + security group + IAM instance profile → EC2 instance → inventory file. The S3 bucket ARN feeds the IAM policy, so the policy can only ever reach this bucket. Terraform works out this order from the references; no `depends_on` is needed.

## How the Ansible code works

`ansible.cfg` points at the generated inventory and the `roles/` folder, disables host-key prompts for new instances and enables SSH pipelining for speed.

**`site.yml`** targets the `web` group with `become: true` (sudo) and:

1. **Pre-tasks** — waits for SSH (`wait_for_connection`), waits for **cloud-init** to finish first boot so apt isn't locked, then gathers facts.
2. **Roles**, in order:

| Role | Tasks |
|---|---|
| `nginx` | Installs Nginx with `apt`; creates the web root; turns `server_tokens off` (validated with `nginx -t`); templates a server block (`site.conf.j2`) with security headers and a `/health` endpoint; enables it and disables the default site; validates config; ensures the service is **started and enabled on boot**. Config changes notify a **handler** that reloads Nginx only when something changed. |
| `website` | Templates `index.html.j2` — a page with an `<h1>Hello, World!</h1>`, the hostname and environment — into the web root; flushes handlers; then **verifies** with `uri` that `http://127.0.0.1/` returns 200 and contains "Hello, World!" (with retries). The play fails if the site isn't actually served. |
| `s3_backup` | Asserts the bucket name came from Terraform; installs the AWS CLI (snap); uploads the deployed page to `s3://<bucket>/site/index.html` **using the instance's IAM role** (no keys on the server); lists the bucket to confirm. Toggle with `s3_backup_enabled`. |

**Variables:** Terraform-provided values (`ansible_host`, key path, `s3_bucket_name`, `aws_region`, `deploy_environment`) live in the generated `hosts.ini`; `inventory/group_vars/web.yml` maps them onto each role's prefixed variables (`nginx_*`, `website_*`, `s3_backup_*`). Each role has `defaults/main.yml` so it also works on its own.

**Idempotency:** modules (`apt`, `template`, `file`, `service`, `lineinfile`) only change what differs; commands use `creates:` or `changed_when:`. A second run reports no changes to the server.

## Testing and CI

```bash
make lint                            # fmt check, validate, syntax-check, ansible-lint
terraform -chdir=terraform test      # offline unit tests with mocked providers
```

`terraform/tests/main.tftest.hcl` mocks every provider, so it needs no AWS credentials and creates nothing. It checks that:

- SSH is limited to the detected IP, or to `ssh_allowed_cidr` when set, and invalid CIDRs are rejected
- HTTP is open on port 80
- IMDSv2 is required, the root volume is encrypted and S3 public access is fully blocked
- the instance uses the project instance profile
- the generated inventory contains the instance IP and bucket name

GitHub Actions (`.github/workflows/ci.yml`) runs `terraform fmt -check`, `terraform validate`, `ansible-playbook --syntax-check` and `ansible-lint` (production profile) on every push.

## Security decisions

- **SSH locked to your IP** (`/32`), never `0.0.0.0/0`.
- **No AWS keys on the server** — the instance uses an IAM role via the metadata service, with **IMDSv2 enforced**.
- **Least-privilege IAM** — the instance can touch only this project's bucket.
- **Private S3 bucket** — public access blocked, ACLs disabled, encrypted, versioned.
- **Encrypted root volume**; Nginx version hidden; basic security headers.
- **Secrets stay out of Git** — `.gitignore` excludes state files, `*.tfvars`, `.keys/`, `*.pem` and the generated inventory.

> For a team setup you would also move Terraform state to a remote backend (S3 + DynamoDB locking) and restrict the security group further (or drop SSH and use SSM only).

## Cost

`t3.micro` + 8 GiB gp3 + a near-empty S3 bucket is covered by the AWS Free Tier for eligible accounts; otherwise it is roughly **$0.01/hour**. Note that AWS charges for public IPv4 addresses (~$0.005/hour). Run `make destroy` when finished.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `No valid credential sources found` | Run `aws configure`, then `aws sts get-caller-identity`. |
| `Error when retrieving token from sso: Token has expired` | Your `default` profile uses IAM Identity Center (SSO). Either run `aws sso login`, or create a profile for your access key with `aws configure --profile techprojects` and `export AWS_PROFILE=techprojects` (on Windows you can start the toolbox with `$env:AWS_PROFILE="techprojects"; docker compose run --rm toolbox`). |
| `UNPROTECTED PRIVATE KEY FILE` / `Permission denied (publickey)` | The key is on a Windows-mounted folder. Use the Docker toolbox (key goes to the `/keys` volume) or clone inside the WSL home folder. |
| Ansible `UNREACHABLE` / SSH timeout | Your public IP changed since `apply`. Run `terraform apply` again (it re-detects the IP and updates the SSH rule), or set `ssh_allowed_cidr`. |
| `[WARNING]: Ansible is being run in a world writable directory ... ignoring it as an ansible.cfg source` | Set `ANSIBLE_CONFIG=$PWD/ansible.cfg` (the Docker toolbox already does). |
| `Unsupported: The requested configuration is currently not supported` for `t3.micro` | That AZ lacks the type; re-run `terraform apply` or set `instance_type = "t2.micro"`. |
| `apt` lock errors | The pre-task waits for cloud-init; re-run the playbook if the instance was still booting. |
| Page not reachable but Ansible succeeded | Use `http://` (not `https://`); check the security group has port 80 open. |
